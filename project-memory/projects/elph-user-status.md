# elph-user-status

## Назначение

Сервис хранит состояния пользователей Elph, ведёт presence и отдаёт их API gateway по gRPC. Рабочий статус УРВ описан в актуальных документах как расширение, но в проверенном коде ещё не реализован.

## Устройство

- Текущий сервис использует PostgreSQL (`ElphUsers`, кастомные статусы, аккаунты), Redis для реестра соединений и публикации событий, а также PostgreSQL NOTIFY и RabbitMQ для существующих потоков.
- `UserStatusService.GetPresence` возвращает снимок присутствия. `UsersWatcher` преобразует изменения `ElphUsers` в событие `UserStatusChangedEvent` для Redis-канала, который слушает gateway.
- В текущих `AppModule`, модели `UserEntity`, gRPC `UserPresence` и `UserStatusChangedEvent` нет `workStatus`; отдельной таблицы рабочих статусов и подписчика снимков УРВ тоже нет.

## Контракты и сценарии

- Целевой сценарий по документам от 2026-11-12: офисный [[elph-bot-jarvis]] выбирает один рабочий статус по двум ответам УРВ за день и передаёт полный снимок через Redis Pub/Sub. `elph-user-status` сопоставляет полный email и домен с пользователем Elph, хранит один готовый статус на пользователя и передаёт его через `GetPresence` и `UserStatusChangedEvent` в [[api-gateway]]. Это ещё предстоит реализовать.
- Планируемый рабочий статус независим от сетевого/DND и текстового. В существующих GraphQL `aggregateElphUserStatuses` и `elphUserStatusChanged` добавляется одно nullable поле `workStatus` с `code`, `startsAt`, `endsAt`; отсутствующая или истёкшая запись даёт `null`. Клиентский TTL не предусмотрен.
- Планируемый внутренний TTL задаётся окружением сервиса; периодическая задача удаляет истёкшие записи. PDF приводит 30 минут только как пример и указывает проход задачи каждые две минуты. Снимок продлевает срок даже без изменения клиентского значения; повтор не должен создавать событие. Для двух экземпляров сервиса нужен общий порядок снимков и защита конкурентной записи.
- При успешно полученной полной выгрузке сотрудник справочника без распознанной позиции и причины получает `outside_office`, включая переход на новый день. При сбое любой статусной ручки Jarvis не публикует пустой снимок; старое значение остаётся до истечения внутреннего срока.
- Целевая карта клиента: обычный вход `office`, выход или отсутствие данных за текущий день `outside_office`, удалёнка `remote_work`, спортзал `gym`, курилка `smoking`; причины `О/ОТ` → `annual_leave`, `У` → `study_leave`, `ОВ/ОЖ` → `parental_leave`, `ДО` → `unpaid_leave`, `ОТГ` → `day_off`, `Б/ББ` → `sick_leave`, `К` → `business_trip`. `other_absence` и `no_data` исключены. Это карта последнего PDF, не реализованный enum.

## Особенности и риски

- PDF «Принцип работы» отдаёт выбор приоритета Jarvis, а сводный PDF в таблице ответственности приписывает применение приоритетов `elph-user-status`. Для технической реализации это противоречие надо разрешить; по подробному потоку сервис статусов получает уже выбранное значение.
- PDF от 2026-11-12 требует серверный переключатель, выключенный по умолчанию; локальная проработка в `docs/urv-work-statuses-implementation.md` утверждает, что отдельный переключатель не нужен. Решение о переключателе не считать согласованным.
- Последний PDF сопоставляет `ОВ` с `parental_leave`, тогда как локальная карта относит `ОВ` к `disabled_child_care_day`. Требуется подтверждение значений УРВ и клиентского кода до реализации.
- При нескольких причинах отсутствия за день правило выбора одного статуса не согласовано. Формат `startsAt`/`endsAt` тоже требует согласования: текст требует исходные даты УРВ без добавления зоны, пример GraphQL использует ISO UTC.
- В текущем `elph-user-status` нет клиента profile-service. Точное сопоставление email с `User.id`, указанное в плане, требует отдельной интеграции и проверки контракта профилей.

## Связи

- [[elph-bot-jarvis]] — планируемый офисный издатель полных снимков; в поставку не входит.
- [[api-gateway]] — текущий gRPC-клиент и внешний GraphQL-вход для чтения/подписки; должен расширить оба маппера.
- [[platform-contracts]] — источник gRPC `UserPresence` и Redis `UserStatusChangedEvent`; оба контракта должны получить рабочий статус.
