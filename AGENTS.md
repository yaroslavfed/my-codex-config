# Инструкции для агента

## Общие правила

- сначала изучай существующую архитектуру, соседние модули и принятые в проекте соглашения
- не вводи новые абстракции, библиотеки или архитектурные слои без необходимости
- предпочитай минимальное изменение, решающее поставленную задачу
- не меняй публичные контракты без явной причины
- учитывай `null` / `undefined`, асинхронность, конкурентный доступ и ошибки внешних систем
- после изменений запускай релевантные проверки проекта
- не считай отсутствие ошибок компилятора доказательством корректности бизнес-логики

## TypeScript / NestJS

Если текущий проект использует TypeScript и NestJS:

- controllers отвечают за transport/API-слой и не должны содержать бизнес-логику
- бизнес-логика находится в сервисах/use-case слоях, если такой подход уже используется в проекте
- доступ к БД должен оставаться в существующем persistence/repository слое
- внешние HTTP/API интеграции должны быть изолированы от бизнес-логики
- учитывай lifecycle NestJS, DI scopes, interceptors, guards, filters и providers
- не создавай циклические зависимости модулей, `forwardRef` используй только как крайнюю меру
- не используй `any`, если тип можно выразить нормально
- не добавляй DTO/тип только ради обёртки одного существующего типа без практической пользы

## Зависимости

- не добавляй новую внешнюю зависимость, если задачу разумно решить средствами языка, стандартной библиотеки или уже используемых зависимостей
- перед добавлением зависимости проверь, нет ли подходящего решения уже в проекте
- не обновляй версии зависимостей без необходимости для текущей задачи
- если новая зависимость необходима, явно объясни, зачем она нужна

## Комментарии и документация в коде

Эти правила применяются ко всем комментариям и встроенной документации в коде, включая:

- обычные однострочные и многострочные комментарии
- XML Documentation Comments и `summary` в C#
- JSDoc и TSDoc в JavaScript и TypeScript
- Javadoc в Java
- аналогичные механизмы документирования в других языках

При написании комментариев и документации соблюдай следующие правила:

- пиши понятно, кратко и без лишней перегрузки
- у последнего предложения не ставь точку
- заглавную букву используй только в начале предложения и там, где она требуется для имени, названия или другого собственного обозначения
- английские слова используй для названий сущностей, технологий, API, типов, методов, параметров и других случаев, где это необходимо
- не вставляй англицизмы в русский текст без необходимости
- не используй длинное тире `—`
- не используй точку с запятой `;` как знак препинания
- двоеточие используй минимально и только когда оно действительно улучшает читаемость
- не пересказывай очевидное поведение кода
- описывай назначение, причины, ограничения, неочевидное поведение и важный контекст
- сохраняй синтаксис и обязательную структуру конкретного формата документации, например XML-теги, JSDoc-теги и Javadoc-теги
- эти правила относятся к тексту внутри документации и не должны нарушать технически необходимый синтаксис языка или инструмента
- не добавляй `summary`, JSDoc, Javadoc и аналогичную документацию к каждому методу или классу автоматически, если она не даёт дополнительной полезной информации

## Неопределённость и предположения

- не додумывай бизнес-логику, если её нельзя уверенно вывести из кода, документации или задачи
- сначала ищи подтверждение в существующей реализации, тестах и соседних модулях
- если приходится сделать предположение, явно укажи его в итоговом ответе
- не выдавай предположение за установленный факт
- если есть несколько разумных вариантов реализации, предпочитай тот, который меньше меняет текущую систему

## Область изменений

- не исправляй проблемы, не относящиеся к текущей задаче, если они не мешают её выполнению
- не выполняй сопутствующий рефакторинг без необходимости
- если обнаружил отдельную проблему, сообщи о ней, но не исправляй автоматически
- не меняй файлы, которые не нужны для решения задачи
- не переформатируй и не перестраивай код вне области необходимых изменений
- избегай diff noise: изменение форматирования, порядка import, переносов строк и других косметических деталей не должно затрагивать несвязанный код без необходимости

## Тесты и проверки

- при изменении поведения найди существующие тесты для затронутой логики
- новые тесты пиши в стиле существующих тестов проекта
- проверяй не только happy path, но и релевантные граничные сценарии
- не удаляй тесты и не ослабляй assertions ради прохождения проверки
- не изменяй тесты только для того, чтобы подогнать их под ошибочную реализацию
- после изменений запускай минимально достаточный набор релевантных тестов, lint и build/typecheck
- если какую-либо проверку запустить не удалось, явно укажи это в результате
- не ослабляй конфигурацию lint, typecheck, тестов или quality gates только ради прохождения проверки
- изменение конфигурации инструментов допустимо только если оно является частью задачи или подтверждённым исправлением самой конфигурации

## Безопасность

- не добавляй секреты, токены, пароли и credentials в код, логи, тестовые данные или документацию
- не ослабляй authentication, authorization, validation, TLS, CORS и другие механизмы безопасности ради упрощения реализации
- пользовательский и внешний ввод считай недоверенным
- не логируй секретные или чувствительные данные
- если задача требует изменения security-механизма, явно укажи последствия в результате

## Сгенерированные файлы

- не редактируй вручную generated-файлы, если существует исходный файл или генератор
- если изменение требует регенерации, изменяй источник и используй существующий механизм генерации
- не запускай массовую регенерацию, если она создаёт несвязанный diff

## Git

- не выполняй `git add`, `git commit`, `git push`, `git merge`, `git rebase`, `git cherry-pick`, `git reset` и другие команды, изменяющие staging area или историю Git, без моего явного запроса
- никогда не создавай коммиты автоматически после выполнения задачи
- разрешается использовать read-only Git-команды для анализа состояния и истории репозитория, например `git status`, `git diff`, `git log`, `git show`, `git branch`, `git blame`, `git merge-base`, `git rev-parse`, `git ls-files`
- при предложении commit message описывай уже выполненное изменение, а не процесс работы над ним
- формулируй содержательную часть commit message в прошедшем времени, например `Исправил обработку участников`, `Добавил валидацию`, `Обновил синхронизацию`
- не используй инфинитивные формулировки вроде `Исправить`, `Добавить`, `Обновить`, а также общие названия вроде `Исправил замечания ревью`, `Правки после ревью`, `Исправления`, которые не объясняют, что именно изменилось
- заголовок коммита должен кратко отражать общее выполненное изменение
- описание коммита, если оно нужно, должно в нескольких словах уточнять, что именно было сделано, без лишних деталей
- служебные префиксы и ссылки на задачу, например `fix refs #524813`, сохраняй, если они требуются соглашениями проекта, но содержательная часть commit message должна описывать выполненное изменение
- после завершения задачи:
  - перечисли изменённые файлы
  - сгруппируй изменения по логическим коммитам
  - предложи commit message для каждого коммита
  - укажи файлы, которые должны войти в каждый коммит
  - сам изменения не индексируй и не коммить

## Работа с WebStorm MCP

- если доступен WebStorm MCP, используй его как основной источник семантической информации о коде
- для поиска usages, definitions, symbols, call hierarchy и IDE problems сначала используй WebStorm MCP, а не `grep`, `rg` или простой текстовый поиск
- если меняется public API, provider, DTO, interface, type, event contract или repository method, обязательно проверь usages через IDE/MCP
- для анализа вызовов используй call hierarchy / analyze calls через MCP, если это помогает подтвердить finding
- для проверки ошибок и предупреждений используй IDE inspections / file problems
- для запуска проекта, тестов, lint, build и debug предпочитай существующие WebStorm Run Configurations, если они подходят задаче
- shell используй для Git, специализированных CLI-команд и случаев, где IDE/MCP не даёт нужной информации
- не заменяй семантический анализ кода простым текстовым поиском, если MCP может дать более точный результат
- если MCP недоступен или нужного tool нет, явно сообщи об этом и используй альтернативный способ
- при review в конце кратко перечисляй, какие IDE/MCP проверки были выполнены

## Правила review

Если задача относится к review:

1. определи цель изменения и merge-base относительно целевой ветки, если она известна
2. анализируй полный diff, а не только изменённые строки
3. читай изменённые файлы в контексте
4. найди usages изменённых public API, типов, providers, DTO и методов
5. проверь call hierarchy там, где это полезно
6. проверь IDE inspections для затронутых файлов
7. найди и запусти связанные тесты, lint или build через подходящие Run Configurations
8. не исправляй код, если пользователь запросил только review
9. не придумывай findings ради количества
10. если гипотеза не подтверждается кодом, usages, тестами или контрактом, отбрасывай её
11. если изменение затрагивает async flow, worker, scheduler, retry, external API или БД, отдельно проверяй race conditions, partial failures и idempotency

## Формат findings

Для review используй только подтверждённые замечания

Каждый finding должен содержать:

- severity: `P0`, `P1`, `P2` или `P3`
- место: файл и строка/символ, если можно определить
- проблему
- доказательство или конкретный сценарий воспроизведения
- влияние
- направление исправления

Если существенных проблем нет, явно напиши `CLEAN`

## Формат результата

После выполнения задачи кратко укажи релевантные пункты:

1. какую проблему/задачу решали
2. что было изменено
3. какие важные решения были приняты
4. какие проверки были выполнены и их результат
5. что не удалось проверить
6. обнаруженные риски или ограничения, если они есть
7. изменённые файлы
8. рекомендуемое разбиение изменений на коммиты согласно разделу Git

Не добавляй пустые или формальные пункты, если соответствующей информации нет

## Язык общения

- всегда отвечай пользователю на русском языке
- findings, root cause, review, verdict, объяснения и рекомендации пиши на русском
- названия классов, методов, API, библиотек, команд и технических терминов можно оставлять на английском
- код сохраняй в стиле существующего проекта
- для комментариев и встроенной документации соблюдай правила раздела «Комментарии и документация в коде», даже если существующие комментарии проекта оформлены иначе
