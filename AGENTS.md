# Инструкции для агента

## Проект

Проект использует TypeScript и NestJS. При работе с кодом:

- сначала изучай существующую архитектуру, соседние модули и принятые в проекте соглашения;
- не вводи новые абстракции, библиотеки или архитектурные слои без необходимости;
- предпочитай минимальное изменение, решающее поставленную задачу;
- не меняй публичные контракты без явной причины;
- учитывай `null` / `undefined`, асинхронность, конкурентный доступ и ошибки внешних систем;
- после изменений запускай релевантные проверки проекта: TypeScript, lint, unit/e2e-тесты;
- используй возможности IDE/MCP для поиска usages, переходов к определениям, инспекций и запуска конфигураций;
- не считай отсутствие ошибок компилятора доказательством корректности бизнес-логики.

## NestJS

- Controllers отвечают за transport/API-слой и не должны содержать бизнес-логику.
- Бизнес-логика находится в сервисах/use-case слоях, если такой подход уже используется в проекте.
- Доступ к БД должен оставаться в существующем persistence/repository слое.
- Внешние HTTP/API интеграции должны быть изолированы от бизнес-логики.
- Учитывай lifecycle NestJS, DI scopes, interceptors, guards, filters и providers.
- Не создавай циклические зависимости модулей; `forwardRef` — крайняя мера, а не стандартное решение.
- Не используй `any`, если тип можно выразить нормально.
- Не добавляй DTO/тип только ради обёртки одного существующего типа без практической пользы.
- Новая зависимость npm должна иметь явное обоснование.

## Работа с Git diff

Если задача относится к review:

1. Определи merge-base относительно целевой ветки, если она известна.
2. Анализируй полный diff, а не только отдельные строки.
3. Читай изменённые файлы в контексте.
4. Найди usages изменённых public API, типов и методов.
5. Проверь связанные тесты.
6. Не исправляй код, если пользователь запросил только review.

## Формат findings

Для review используй только подтверждённые замечания.

Каждый finding:

- severity: `P0`, `P1`, `P2` или `P3`;
- место: файл и строка/символ, если можно определить;
- проблема;
- доказательство или конкретный сценарий воспроизведения;
- влияние;
- направление исправления.

Не придумывай замечания ради количества. Если существенных проблем нет, явно напиши `CLEAN`.

## Язык общения

- Всегда отвечай пользователю на русском языке.
- Названия классов, методов, переменных, API, библиотек, команд и технических терминов можно оставлять на английском, если это естественно для контекста.
- Код и комментарии в коде сохраняй в стиле и языке существующего проекта.
- Findings, объяснения, выводы review, описание root cause и рекомендации пиши на русском.
