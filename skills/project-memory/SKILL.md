# Память проекта

Память хранится отдельно от скилла: `../../project-memory` относительно **реального каталога** этого `SKILL.md`. Разрешай символическую ссылку на скилл перед вычислением пути. Ожидаемая структура: `README.md` и `projects/<имя-репозитория>/<имя-репозитория>.md` с тематическими заметками в той же папке. `projects/` можно открыть как хранилище Obsidian. Не используй старые `pmem`, SQLite и JSON как текущую память.

Если каталога памяти нет, кратко сообщи путь пользователю и продолжай основную задачу без ошибки. Не создавай отсутствующий корневой каталог автоматически: возможно, скилл установлен отдельно от памяти. Если каталог есть, но нет папки нужного репозитория, создай её и обзорную заметку при появлении подтверждённого знания.

## Чтение

1. Определи репозиторий по корню Git или явному контексту пользователя. Имя папки и обзорной заметки равно имени каталога репозитория. Если имена совпадают у разных репозиториев, уточни идентичность до записи и не смешивай сведения.
2. Для конкретного репозитория сначала открой `projects/<имя>/<имя>.md`, затем только подходящие тематические заметки по ссылкам из обзора. Для вопроса без известного репозитория начни с `projects/Карта сервисов.md` или ищи точные термины в `projects/` рекурсивно, затем читай только найденные файлы и связанные с ними заметки. Не загружай весь каталог без необходимости.
3. Используй заметку как навигатор: проверь важные для текущего вывода сведения в актуальном коде, контрактах или тестах. Если исходный репозиторий недоступен, укажи дату и границу прежней проверки; не называй записанное текущим поведением без новой проверки.
4. Для вопроса о сервисах или API отвечай по подтверждённым данным, указывай репозиторий, публичный маршрут или контракт и неопределённость, если она осталась.

## Запись

Пиши только сведения, которые помогут в следующих задачах: устройство и ответственность сервиса, важные потоки, публичные контракты и ручки, связи с другими репозиториями, неочевидные ограничения, инварианты и подтверждённые риски. Сначала проверь первоисточник и поищи в заметке эквивалентную запись. Не сохраняй догадки, временное состояние ветки, отдельные результаты тестового запуска, тривиальные местоположения файлов или пересказ diff.

Обзорную заметку репозитория держи короткой: назначение, ссылки на темы и связи с другими репозиториями. Подтверждённые сведения о небольшом репозитории могут оставаться в обзоре, не создавай пустые тематические файлы. Для отдельного устойчивого сценария или области ответственности создай тематическую заметку в папке репозитория. Не дроби память по классам и методам без практической причины. В каждой заметке с фактами указывай относящиеся к ним источники: пути к коду **от корня исходного репозитория**, символы, дату и ветку проверки; внешние документы обозначай отдельно. Явно отделяй текущее поведение, сведения из отдельной ветки, целевой план и известные ограничения. Не выдавай проверенное в отдельной ветке за состояние основной ветки.

При изменении знаний правь существующий пункт на месте или удаляй устаревший. Если новый код опровергает память, сначала разреши противоречие по коду, затем обнови заметку. Не добавляй рядом вторую версию того же факта. Существенное историческое решение оставляй только тогда, когда оно объясняет действующий контракт или ограничение, с явной пометкой о прошлом состоянии.

Для Obsidian используй обычный Markdown и ссылки относительно `projects/`: `[[имя-репозитория]]` для уникальной обзорной заметки и `[[имя-репозитория/тема|название]]` для тематической. Обзор должен ссылаться на все тематические заметки своей папки. В разделе `Связи` поясняй роль связи, а не оставляй голую ссылку. По возможности добавляй обратную связь в заметку другого репозитория. Не создавай ссылок на несуществующие заметки и не подменяй содержание тегами.

Запись в память не заменяет основную работу и её проверки. Не меняй Git staging area, историю или remote в рамках этого скилла. Кратко упомяни в результате, если память создана или обновлена.
