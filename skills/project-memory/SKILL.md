# Память проекта

Память хранится отдельно от скилла: `../../project-memory` относительно **реального каталога** этого `SKILL.md`. Разрешай символическую ссылку на скилл перед вычислением пути. Ожидаемая структура: `README.md` и `projects/<имя-репозитория>.md` без вложенных групп проектов. Не используй старые `pmem`, SQLite и JSON как текущую память.

Если каталога памяти нет, кратко сообщи путь пользователю и продолжай основную задачу без ошибки. Не создавай отсутствующий корневой каталог автоматически: возможно, скилл установлен отдельно от памяти. Если каталог есть, но нет файла нужного репозитория, создай его в `projects/` при появлении подтверждённого знания.

## Чтение

1. Определи репозиторий по корню Git или явному контексту пользователя. Имя файла равно имени каталога репозитория. Если имена совпадают у разных репозиториев, уточни идентичность до записи и не смешивай сведения.
2. Для конкретного репозитория сначала открой `projects/<имя>.md`. Для вопроса без известного репозитория ищи точные термины по `projects/*.md`, затем читай только найденные файлы и связанные с ними заметки. Не загружай весь каталог без необходимости.
3. Используй заметку как навигатор: проверь важные для текущего вывода сведения в актуальном коде, контрактах или тестах. Если исходный репозиторий недоступен, укажи дату и границу прежней проверки; не называй записанное текущим поведением без новой проверки.
4. Для вопроса о сервисах или API отвечай по подтверждённым данным, указывай репозиторий, публичный маршрут или контракт и неопределённость, если она осталась.

## Запись

Пиши только сведения, которые помогут в следующих задачах: устройство и ответственность сервиса, важные потоки, публичные контракты и ручки, связи с другими репозиториями, неочевидные ограничения, инварианты и подтверждённые риски. Сначала проверь первоисточник и поищи в заметке эквивалентную запись. Не сохраняй догадки, временное состояние ветки, отдельные результаты тестового запуска, тривиальные местоположения файлов или пересказ diff.

Создавай один файл на репозиторий. Начни с коротких разделов `Назначение`, `Устройство`, `Контракты и сценарии`, `Особенности и риски`, `Связи`, `Источники`; заполняй только подтверждённые разделы. В `Источниках` указывай пути **от корня репозитория**, символы и дату/ветку проверки, чтобы сведения можно было перепроверить. Для общих утверждений отделяй подтверждённое поведение от известных ограничений.

При изменении знаний правь существующий пункт на месте или удаляй устаревший. Если новый код опровергает память, сначала разреши противоречие по коду, затем обнови заметку. Не добавляй рядом вторую версию того же факта. Существенное историческое решение оставляй только тогда, когда оно объясняет действующий контракт или ограничение, с явной пометкой о прошлом состоянии.

Для Obsidian используй обычный Markdown и ссылки `[[имя-репозитория]]` между существующими файлами в `projects/`. В разделе `Связи` поясняй роль связи, а не оставляй голую ссылку. По возможности добавляй обратную связь в заметку другого репозитория. Не создавай ссылок на несуществующие заметки и не подменяй содержание тегами.

Запись в память не заменяет основную работу и её проверки. Не меняй Git staging area, историю или remote в рамках этого скилла. Кратко упомяни в результате, если память создана или обновлена.
