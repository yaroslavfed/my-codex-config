# Code Review

Используй этот skill для обычного инженерного review изменений.

## Цель

Найти реальные дефекты и регрессии, а не максимальное количество замечаний.

## Алгоритм

1. Определи область изменений:
   - git diff / merge-base;
   - изменённые файлы;
   - затронутые публичные методы, DTO, события, схемы БД и конфигурация.

2. Прочитай изменённые файлы целиком в необходимом контексте.

3. Через IDE/MCP:
   - найди usages изменённых символов;
   - проверь инспекции IDE;
   - перейди к определениям зависимостей;
   - найди связанные тесты.

4. Проверь:

### Correctness
- соответствует ли реализация заявленному поведению;
- off-by-one, неправильные условия, пропущенные ветки;
- `null` / `undefined`;
- преобразования дат, таймзон, идентификаторов и enum;
- ошибки сериализации/десериализации.

### Async / concurrency
- забытые `await`;
- fire-and-forget;
- race conditions;
- двойная обработка;
- идемпотентность;
- транзакционные границы;
- повторные запросы / retry.

### Contracts
- API DTO;
- database schema;
- внешние интеграции;
- event/message contracts;
- обратная совместимость.

### Error handling
- потерянные исключения;
- слишком широкий catch;
- ошибочная классификация 4xx/5xx;
- частично выполненные операции;
- cleanup ресурсов.

### NestJS
- DI и provider scope;
- module boundaries;
- lifecycle hooks;
- guards/interceptors/filters;
- бизнес-логика в controller;
- циклические зависимости.

### Tests
- тестируется ли изменённое поведение;
- есть ли негативные сценарии;
- тесты действительно падают при регрессии;
- нет ли тестов, проверяющих реализацию вместо поведения.

### Maintainability
Отмечай только если это создаёт конкретный риск:
- дублирование логики;
- скрытая связность;
- неочевидные side effects;
- лишняя сложность.

5. По возможности запусти релевантные проверки через IDE:
   - tests;
   - typecheck;
   - lint;
   - существующие run configurations.

## Формат ответа

Сначала findings по severity: `P0 → P3`.

Для каждого:

**[P1] Короткое название**

- Где: `path/to/file.ts:line`
- Проблема:
- Сценарий:
- Влияние:
- Исправление:

После findings:

- `CLEAN`, если существенных проблем нет;
- кратко перечисли выполненные проверки;
- отдельно укажи то, что не удалось проверить.

## Запрещено

- придумывать дефект только ради finding;
- считать style preference дефектом;
- переписывать код без запроса;
- делать вывод о корректности только по тестам или компиляции.
