# Branch report

Подготавливай по diff текущей ветки два отдельных готовых текста:

1. текст для Merge Request
2. текст для Redmine

Не изменяй код, staging area или историю Git. Используй только read-only Git-команды.

## Определение diff

1. Определи текущую ветку
2. Определи целевую ветку:
   - используй явно указанную пользователем target branch
   - если она не указана, попробуй определить default branch репозитория
   - если default branch нельзя определить уверенно, используй наиболее вероятную целевую ветку только при наличии достаточных признаков в репозитории
   - если выбор target branch существенно влияет на результат и его нельзя определить, явно укажи это
3. Найди merge-base текущей и целевой ветки
4. Анализируй полный diff от merge-base до текущего HEAD
5. Читай изменённые файлы в контексте, а не делай выводы только по списку файлов
6. При необходимости используй историю ветки, тесты, документацию и связанные участки кода, чтобы понять смысл изменения
7. Не включай в описание изменения, которых нет в diff текущей ветки

## Общие правила

- описывай фактически выполненные изменения
- не пересказывай diff построчно
- объединяй связанные изменения в несколько смысловых пунктов
- не перегружай текст деталями реализации
- не используй общие формулировки вроде `Исправлены замечания`, `Внесены правки`, `Доработан код`, если можно назвать конкретное изменение
- не выдумывай бизнес-эффект, причину дефекта, сценарий использования или способ проверки
- если причина дефекта не подтверждается кодом, тестами, историей или контекстом задачи, не назначай виновника и не представляй предположение как факт
- не указывай имена разработчиков как виновников проблемы, если пользователь явно не попросил об этом и это не подтверждено надёжными данными
- если часть вывода является предположением, пометь её как предположение или не включай её
- пиши на русском языке

# Текст для Merge Request

MR должен быть техническим, коротким и понятным разработчику или ревьюеру.

## Заголовок

- одна строка
- отражает общий технический результат изменений
- описывает, что сделано, а не процесс работы
- не используй формулировки вроде `Исправление замечаний ревью`, `Правки`, `Доработки`
- не перечисляй все мелкие изменения

Пример подхода:

```text
Исправлена синхронизация участников событий Nextcloud
```

## Описание

- краткое summary по diff ветки
- обычно 2-5 пунктов
- описывай изменения с технической точки зрения
- указывай важные изменения контрактов, flow, хранения данных, обработчиков, интеграций или тестов, если они существенны
- не описывай очевидные механические изменения
- не превращай описание в техническую документацию

Используй Markdown, если MR поддерживает Markdown.

Формат ответа:

```text
MR

Заголовок:
<заголовок>

Описание:
<готовый текст>
```

# Текст для Redmine

Redmine должен объяснять изменение прежде всего с точки зрения поведения системы, проблемы пользователя или бизнес-сценария. Технические детали добавляй только там, где они помогают понять причину или результат.

Используй минимальный Textile-синтаксис Redmine, а не Markdown.

## Разрешённое оформление

Не используй `h1.`, `h2.`, `h3.` и другие уровни заголовков. Они визуально перегружают описание.

Используй только базовое оформление:

```text
*Заголовок или подзаголовок*

Обычный текст

* пункт перечисления
* ещё один пункт

# первый шаг
# второй шаг

@код или техническое имя@
```

Правила оформления:

- заголовок и подзаголовки оформляй только жирным текстом через `*текст*`
- обычные пояснения пиши простым текстом
- технические имена, команды, значения и короткие фрагменты кода при необходимости оформляй через `@текст@`
- для порядка действий используй нумерованный список `#`
- для обычного перечисления используй маркированный список `*`
- не используй Markdown-заголовки, fenced code blocks, таблицы и сложное форматирование
- не злоупотребляй выделением, жирным должны быть в основном только смысловые заголовки и подзаголовки

## Структура Redmine

Подбирай только релевантные блоки. Не создавай пустые разделы.

### Для дефекта

Если изменение исправляет дефект и первопричину можно подтвердить, используй структуру:

```text
*Причина*

<откуда возникла проблема и почему старое поведение было неверным>

*Что изменено*

<как работало раньше и как работает теперь>

*Проверка*

<информация для QA>
```

В блоке `Причина`:

- объясни первопричину понятным языком
- укажи, какое условие или сценарий приводил к проблеме
- при необходимости кратко объясни техническую причину
- не назначай виновника без явного запроса и подтверждённых данных

В блоке `Что изменено`:

- сначала опиши прежнее поведение, если это помогает понять изменение
- затем опиши новое поведение
- перечисли существенные связанные изменения
- делай акцент на результате для пользователя или системы, а не на названиях классов и методов

### Для обычной задачи

Если это не дефект, блок `Причина` не нужен. Обычно используй:

```text
*Что сделано*

<что изменилось и зачем>

*Проверка*

<информация для QA>
```

При необходимости можно добавить короткий подзаголовок для важных ограничений или затронутых сценариев, также оформленный только жирным текстом.

## Блок проверки

Сформируй понятную информацию для QA:

- основной ручной сценарий проверки
- ожидаемый результат
- релевантные граничные сценарии
- смежные участки, которые могли быть затронуты изменением
- автоматические проверки, если они действительно помогают QA понять покрытие

Для пошагового сценария используй нумерованный Textile-список:

```text
*Проверка*

# Выполнить ...
# Проверить ...
# Убедиться, что ...
```

Для перечисления затронутых сценариев используй обычный Textile-список:

```text
*Затронутые сценарии*

* сценарий ...
* сценарий ...
```

Не придумывай недоступные пользователю действия или данные. Если точный ручной сценарий нельзя вывести из изменений, опиши только те проверки, которые можно обосновать.

## Объём Redmine

Redmine должен быть подробнее MR, но без лишней воды.

Ориентир:

- причина: 1-2 коротких абзаца
- что изменено: 1 короткий абзац и/или 2-6 пунктов
- проверка: короткий пошаговый сценарий и только необходимые смежные проверки

# Финальный ответ

Всегда выводи два отдельных текста в следующем порядке:

1. `MR`
2. `Redmine`

Не смешивай их между собой и не добавляй длинное вступление перед готовыми текстами.
