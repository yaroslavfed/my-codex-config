# Bug Hunt

Используй этот skill для проактивного поиска потенциальных дефектов в коде, diff или реализации.

Если уже есть конкретный наблюдаемый симптом, падающий тест, runtime error, CI failure или воспроизводимая проблема, используй `systematic-debugging` вместо этого skill.

## Главное правило

Не придумывай проблемы ради количества findings.

Каждый потенциальный баг должен опираться на конкретный execution path, входные данные, состояние или контракт, при которых поведение действительно становится неверным.

## Workflow

### 1. Определи область поиска

Сначала пойми:

- что именно изменилось или какую область кода нужно проверить
- какие публичные контракты и side effects затронуты
- какие callers и consumers зависят от этой логики
- какие данные приходят извне

Не расширяй анализ на весь проект без необходимости.

### 2. Построй execution paths

Для релевантной логики проследи пути вида:

`entry point -> validation -> service -> persistence/external system -> output`

Отдельно рассматривай:

- success path
- empty/null/undefined input
- invalid input
- partial failure
- retry/repeated execution
- concurrent execution
- timeout/external failure
- boundary values

### 3. Проверяй инварианты и предположения

Ищи места, где код молча предполагает, что:

- значение всегда существует
- коллекция не пуста
- timezone/locale фиксированы
- порядок событий гарантирован
- операция выполняется только один раз
- внешний сервис всегда возвращает ожидаемый shape
- запись в БД всегда успешна
- состояние не изменяется конкурентно

Finding должен объяснять, какое предположение нарушается и к чему это приводит.

### 4. Сверься с контрактами и аналогами

Используй:

- tests
- DTO/schema/validation
- repository contracts
- API contracts
- соседнюю работающую реализацию
- usages/call hierarchy
- релевантную git history при необходимости

Не считай отличие от соседнего кода багом само по себе.

### 5. Оцени реальность бага

Перед тем как оставить finding, ответь:

1. Есть ли достижимый сценарий?
2. Есть ли конкретное неверное поведение?
3. Связано ли оно с проверяемым кодом или diff?
4. Не блокирует ли сценарий validation или другой слой раньше?
5. Не является ли это уже ожидаемым поведением по контракту?

Если доказательств недостаточно, отбрось finding или явно обозначь его как неподтверждённый риск.

### 6. Для подтверждённого бага

Опиши:

- trigger
- execution path
- фактическое неверное поведение
- ожидаемое поведение
- root cause в проверяемом коде
- минимальный способ исправления
- regression test, если он уместен

Не исправляй unrelated проблемы, обнаруженные по пути.

## Результат

Для каждого подтверждённого finding укажи:

1. Severity
2. Где находится проблема
3. Сценарий воспроизведения
4. Почему текущее поведение неверно
5. Root cause
6. Минимальное исправление
7. Что проверить тестом

Если подтверждённых дефектов нет:

`BUG HUNT: CLEAN`
