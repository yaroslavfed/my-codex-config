# Documentation Conformance Review

## Purpose

Use this skill to verify that an implementation fully conforms to the project documentation.

The documentation is the primary source of truth for expected behavior, architecture, contracts, flows, responsibilities, constraints, and implementation requirements.

The reviewer must verify both directions:

1. The implementation satisfies everything required by the documentation.
2. The documentation itself is internally consistent and describes one unambiguous solution.

The goal is not merely to find code defects. The goal is to detect any divergence between:

- documented behavior;
- implemented behavior;
- documented architecture;
- implemented architecture;
- documented contracts;
- implemented contracts;
- different parts of the documentation itself.

---

# Core Principle

## Documentation is the source of truth

Unless the documentation contradicts itself, assume that the documented solution is intentional and authoritative.

Do not silently reinterpret documentation based on:

- the current implementation;
- personal preference;
- common framework conventions;
- what would be easier to implement;
- what appears to be a "better" architecture.

If the implementation and documentation disagree, treat the implementation as incorrect unless there is evidence that the documentation itself is inconsistent.

Do not "fix" the interpretation by assuming that the code represents a newer decision.

Explicitly report the discrepancy.

---

# Mandatory Review Order

Perform the review in this order:

1. Understand the documentation.
2. Validate the documentation for internal consistency.
3. Extract explicit and implicit implementation requirements.
4. Inspect the implementation.
5. Map documented requirements to implementation.
6. Detect missing, partial, incorrect, or extra behavior.
7. Verify end-to-end flows.
8. Produce findings with direct documentation-to-code traceability.

Do not start judging implementation details before understanding the documented system.

---

# Phase 1 — Documentation Analysis

Read all documentation relevant to the reviewed feature.

Build a mental model of:

- actors;
- services;
- modules;
- components;
- commands;
- API endpoints;
- RPC methods;
- events;
- queues;
- topics;
- webhooks;
- storage;
- database entities;
- state transitions;
- authentication;
- authorization;
- error handling;
- retries;
- idempotency;
- timeouts;
- security constraints;
- ownership boundaries;
- data flows;
- lifecycle flows;
- creation flows;
- update flows;
- deletion/revocation flows.

Pay special attention to words such as:

- MUST;
- SHOULD;
- SHALL;
- required;
- always;
- never;
- only;
- before;
- after;
- first;
- then;
- in case of;
- if;
- otherwise;
- must not;
- responsible for;
- source of truth;
- stored in;
- generated by;
- sent to;
- returned to.

These often define requirements that may be easy to miss during implementation.

---

# Phase 2 — Documentation Consistency Check

Before validating the implementation, verify that the documentation itself describes a single coherent solution.

Look for contradictions between:

- different sections;
- prose and diagrams;
- diagrams and sequence diagrams;
- architecture diagrams and API descriptions;
- API examples and schemas;
- one flow and another flow;
- lifecycle descriptions;
- naming;
- ownership descriptions;
- service responsibilities;
- storage responsibilities;
- protocol descriptions;
- security requirements.

Examples:

- one section says `Bot Service` generates a token while another says `Profile Service` generates it;
- one diagram sends an event through RabbitMQ while another describes synchronous gRPC;
- one section says the webhook secret is stored encrypted while another says it is never persisted;
- `/newbot` creates the bot immediately in one section but requires confirmation in another;
- one schema marks a field optional while another flow assumes it is mandatory;
- one section says clients receive menu commands through REST while another says commands are part of WebSocket room state.

---

# Critical Rule: Never Resolve Documentation Contradictions Silently

If two authoritative parts of the documentation describe incompatible behavior, do not choose one interpretation yourself.

Stop treating the affected requirement as unambiguous.

Report the contradiction explicitly.

Use the following structure:

## Documentation conflict

**Topic:** short name of the conflicting decision.

**Variant A**

Where it is described:
`<document / section / diagram>`

What it requires:
`<description>`

**Variant B**

Where it is described:
`<document / section / diagram>`

What it requires:
`<description>`

**Why they conflict**

Explain why both behaviors cannot simultaneously be true.

**Implementation currently follows**

`Variant A`, `Variant B`, `neither`, or `mixed behavior`.

**Decision required**

Present the smallest reasonable set of choices.

For example:

- Option A — make Variant A canonical and update all conflicting documentation.
- Option B — make Variant B canonical and update all conflicting documentation.
- Option C — define explicit conditions under which both variants are valid.

Do not recommend a choice unless there is objective project evidence supporting it.

The final documentation must contain one coherent rule without ambiguous interpretations.

---

# Phase 3 — Requirement Extraction

Convert documentation into concrete review requirements.

Do not only extract large features.

Extract also:

- ordering constraints;
- negative requirements;
- ownership boundaries;
- validation rules;
- edge cases;
- state transitions;
- error scenarios;
- security rules;
- retry rules;
- idempotency rules;
- persistence rules;
- transport requirements;
- cleanup behavior.

Example:

Documentation:

> When `/newbot` succeeds, the platform creates the bot, generates credentials, persists bot metadata, and returns the token once. The token must not be retrievable later.

Derived requirements:

- `/newbot` exists;
- successful creation persists bot metadata;
- credentials are generated;
- token is returned during creation;
- token is not exposed through later read methods;
- there must be no endpoint that leaks the token later;
- failure after partial creation must not leave inconsistent state;
- repeated requests must behave according to documented idempotency semantics, if specified.

Review all derived requirements, not only the most obvious one.

---

# Requirement Traceability

For every meaningful documentation requirement, determine its implementation status.

Allowed statuses:

- `IMPLEMENTED`
- `PARTIALLY_IMPLEMENTED`
- `NOT_IMPLEMENTED`
- `IMPLEMENTED_DIFFERENTLY`
- `NOT_VERIFIABLE`
- `DOCUMENTATION_CONFLICT`

Do not use vague statuses such as:

- "mostly fine";
- "probably implemented";
- "looks okay";
- "seems supported".

---

# Phase 4 — Implementation Inspection

Inspect the actual implementation rather than relying on filenames or expected architecture.

Follow real call chains.

For example:

`HTTP/gRPC/event/command entrypoint`
→ controller/handler
→ application/service logic
→ repository/client
→ external dependency
→ persistence/event/public response

Check:

- where the flow actually begins;
- which branches are reachable;
- which service owns the operation;
- where validation happens;
- where persistence happens;
- which data is returned;
- which events are emitted;
- whether cleanup happens on failures;
- whether all documented branches exist.

Search usages before concluding that a method, DTO, event, type, or service is unused.

---

# End-to-End Flow Verification

Documentation often describes flows rather than isolated functions.

Verify flows end to end.

For each documented flow, reconstruct:

1. trigger;
2. entrypoint;
3. validation;
4. business logic;
5. persistence;
6. communication with other services;
7. event publication;
8. response;
9. failure handling;
10. final state.

Examples:

- bot creation;
- `/newbot`;
- token generation;
- bot deletion;
- revoke;
- webhook registration;
- webhook delivery;
- retry;
- command registration;
- menu command synchronization;
- inline button processing;
- user linking;
- authentication;
- permission checks.

A flow is not considered implemented merely because every mentioned class exists.

The actual runtime path must produce the behavior described by the documentation.

---

# Partial Implementation Detection

Be strict about partially implemented features.

Examples:

Documentation requires:

`create bot → save metadata → issue token → return token`

Implementation only:

`create bot → save metadata`

Status:

`PARTIALLY_IMPLEMENTED`

Do not mark a feature implemented because its main happy-path method exists.

Also verify:

- documented errors;
- side effects;
- state changes;
- follow-up actions;
- cleanup;
- external communication.

---

# Architectural Conformance

Verify documented service boundaries.

Look for violations such as:

- service accesses another service's database directly;
- component owns responsibility assigned to another component;
- REST is used where documentation explicitly requires gRPC;
- synchronous RPC is used where documentation requires an event;
- event publishing occurs in the wrong service;
- API Gateway contains business logic assigned to a domain service;
- duplicated business rules exist in several services;
- external clients access internal service APIs directly.

Do not judge architecture based solely on generic best practices.

Judge it primarily against the documented architecture.

General engineering principles may be reported separately only when they do not contradict documented intent.

---

# Contract Verification

When documentation defines a contract, verify it precisely.

Check:

- route/method name;
- HTTP verb;
- gRPC method;
- protobuf message;
- request fields;
- response fields;
- optionality;
- nullability;
- enum values;
- error codes;
- status codes;
- event name;
- event payload;
- serialization format;
- headers;
- authentication;
- authorization;
- webhook payload;
- command syntax.

Small contract differences matter.

Examples:

Documentation:

`POST /bots/{botId}/webhook`

Implementation:

`PUT /bot/{id}/webhook`

This is a documentation mismatch even if functionality is otherwise equivalent.

---

# Sequence Verification

Pay special attention to ordering.

These are not necessarily equivalent:

`persist → publish event`

and

`publish event → persist`

Likewise:

`validate → generate token`

and

`generate token → validate`

If documentation defines the sequence explicitly, verify that sequence.

Report differences when ordering affects:

- consistency;
- security;
- retries;
- idempotency;
- observable behavior.

---

# Negative Requirements

Explicitly verify things the documentation says must NOT happen.

Examples:

- token must never be logged;
- service must not access another service's DB;
- Bot API must not expose internal IDs;
- webhook secret must not be returned after creation;
- clients must not invoke internal gRPC methods.

Negative requirements are as important as positive requirements.

---

# Documentation Gaps

Distinguish contradictions from missing documentation.

A gap exists when implementation requires a decision but documentation does not define it.

Examples:

- retry count is unspecified;
- timeout behavior is undefined;
- duplicate command behavior is not described;
- two simultaneous `/newbot` requests are not addressed;
- webhook response timeout is unspecified.

Report as:

`DOCUMENTATION GAP`

Do not invent a requirement and then accuse the implementation of violating it.

Instead state:

- what is unspecified;
- why it matters;
- what implementation currently does;
- whether that behavior should be documented.

---

# Extra Implementation Behavior

Also detect behavior that exists in code but is not represented in documentation.

Classify it as:

`UNDOCUMENTED_BEHAVIOR`

Examples:

- extra endpoint;
- additional retry mechanism;
- hidden validation rule;
- undocumented state;
- undocumented event;
- automatic fallback;
- additional authorization requirement.

Do not automatically call undocumented behavior incorrect.

State whether it:

- changes the public contract;
- changes architecture;
- changes observable behavior;
- is merely an internal implementation detail.

If externally meaningful, documentation should normally describe it.

---

# Priority Rules

Use these priorities.

## BLOCKER

Use when:

- documentation is internally contradictory on a core architectural or behavioral decision;
- implementation fundamentally follows a different architecture;
- a mandatory documented flow cannot work;
- critical security guarantees are violated;
- implementation contradicts the public contract.

## HIGH

Use when:

- major documented behavior is missing;
- lifecycle flow is incomplete;
- implementation produces different externally visible behavior;
- service responsibility differs materially from documentation.

## MEDIUM

Use when:

- edge case is missing;
- error handling differs;
- sequence differs but normal happy path still works;
- documentation and implementation differ in a secondary contract detail.

## LOW

Use when:

- terminology differs;
- documentation is stale in a minor non-behavioral detail;
- implementation contains small undocumented internal behavior.

Do not inflate severity.

---

# Evidence Requirements

Every finding must contain evidence from both sides whenever possible.

Required format:

## [SEVERITY] Finding title

**Documentation**

`<document section / quote / requirement>`

**Implementation**

`<file>:<line or symbol>`

**Mismatch**

Explain exactly what differs.

**Impact**

Explain what user-visible, architectural, security, or maintenance consequence follows.

**Required resolution**

Describe what must become consistent.

If documentation is authoritative and unambiguous:

- implementation should change.

If documentation contradicts itself:

- do not prescribe an implementation change until the documentation decision is resolved.

---

# Never Hide Uncertainty

If a requirement cannot be verified because code, configuration, migrations, infrastructure, generated code, or another repository is unavailable, say:

`NOT_VERIFIABLE`

Explain what evidence is missing.

Do not infer implementation from naming alone.

---

# Do Not Overreview

This skill is primarily about documentation conformance.

Do not flood the result with unrelated stylistic issues.

A general code quality issue should be reported only when it materially affects:

- documented behavior;
- correctness;
- architecture;
- security;
- maintainability of the documented flow.

Dedicated language/framework review skills should handle ordinary code-style concerns.

---

# Final Review Output

Use this structure.

# Documentation Conformance Review

## Summary

Briefly state:

- whether implementation broadly matches documentation;
- how many meaningful mismatches were found;
- whether documentation contradictions exist;
- whether any requirements could not be verified.

Do not use vague approval language if significant findings exist.

---

## Documentation conflicts

Include this section first if contradictions were found.

For every conflict describe:

- conflicting statements;
- their locations;
- why they cannot both be correct;
- what implementation currently follows;
- possible resolutions.

End each unresolved conflict with:

`Decision required before this requirement can be considered authoritative.`

---

## Implementation mismatches

List implementation/documentation discrepancies ordered by severity.

---

## Missing documented behavior

List requirements that are explicitly documented but absent from implementation.

---

## Partial implementations

List flows where some documented steps exist but the entire flow is incomplete.

---

## Undocumented behavior

List meaningful externally visible or architectural behavior found in implementation but absent from documentation.

---

## Documentation gaps

List decisions required by implementation that documentation leaves undefined.

---

## Requirement Coverage

Summarize important requirements using:

| Requirement | Documentation | Implementation | Status |
|---|---|---|---|
| ... | ... | ... | IMPLEMENTED |
| ... | ... | ... | PARTIALLY_IMPLEMENTED |
| ... | ... | ... | NOT_IMPLEMENTED |
| ... | ... | ... | IMPLEMENTED_DIFFERENTLY |
| ... | ... | ... | DOCUMENTATION_CONFLICT |
| ... | ... | ... | NOT_VERIFIABLE |

Do not create rows for trivial wording.

Focus on meaningful behavioral, contractual, and architectural requirements.

# Decision Handling

When documentation contains contradictory decisions, do not continue as if one variant were canonical.

Present the choice clearly.

Example:

## Decision required: webhook delivery ownership

Documentation currently contains two incompatible models.

### Option A — Bot API owns delivery

`Bot API → developer webhook`

Implications:

- Bot API owns retry policy;
- Bot API owns signing;
- Bot API owns delivery status.

### Option B — Webhook Worker owns delivery

`Bot API → queue → Webhook Worker → developer webhook`

Implications:

- Bot API only publishes delivery jobs;
- worker owns retries and HTTP delivery;
- worker owns delivery status.

Current implementation follows Option B.

Choose which model is canonical. After the decision, all documentation sections and diagrams describing the other model must be updated.

Do not accept leaving both descriptions in documentation without explicitly documented conditions separating them.

---

# Anti-Patterns

Never do the following.

### Do not treat existing code as truth

Bad:

> Documentation says A, but code currently does B, so documentation is probably outdated.

Correct:

> Documentation says A while implementation does B. Unless documentation is updated intentionally, this is a mismatch.

---

### Do not resolve contradictions by guessing intent

Bad:

> The architecture diagram probably means RabbitMQ, so I ignored the gRPC section.

Correct:

> One section requires RabbitMQ while another requires gRPC. The documentation is contradictory and requires a decision.

---

### Do not validate only class existence

Bad:

> `WebhookService` exists, therefore webhook support is implemented.

Correct:

Trace the real webhook flow through registration, persistence, delivery, security, retries, and errors.

---

### Do not ignore diagrams

Architecture diagrams, sequence diagrams, Mermaid diagrams, tables, schemas, and prose are all part of the documentation.

If prose and diagram disagree, report the conflict.

---

### Do not treat implementation details as requirements

If documentation only says:

> Generate a token.

Do not complain that the project uses UUID instead of ULID unless documentation specifies the token format or the choice introduces an actual correctness/security issue.

---

# Review Mindset

Think like a specification compliance reviewer.

Continuously ask:

- Where exactly is this requirement documented?
- Where exactly is it implemented?
- Does the implementation perform every documented step?
- Does it perform them in the documented order?
- Does it preserve the documented ownership boundaries?
- Does the public contract match exactly?
- Are failure paths represented?
- Are negative requirements respected?
- Does another part of the documentation contradict this statement?
- Is the code introducing behavior the documentation never mentions?
- Could two developers read this documentation and implement materially different systems?

If the answer to the last question is yes, identify the ambiguity.

---

# Completion Criteria

The review is complete only when:

1. all relevant documentation has been inspected;
2. internal documentation contradictions have been checked;
3. major requirements have been extracted;
4. documented flows have been traced through implementation;
5. public contracts have been compared;
6. architectural ownership has been verified;
7. missing and partial behavior has been identified;
8. meaningful undocumented behavior has been identified;
9. documentation gaps have been reported;
10. unresolved contradictions have been surfaced as explicit decisions.

The desired final state is:

`Documentation = one coherent specification`

and

`Implementation = faithful realization of that specification`.
