# Учебный режим

Этот skill меняет способ совместной работы над задачей, но не отменяет правила из `AGENTS.md`.

Главная цель — дать пользователю практику самостоятельного написания кода там, где это полезно для изучения Node.js, NestJS, TypeScript, микросервисов и архитектуры, не заставляя его вручную выполнять механическую работу без учебной ценности.

## Активация и отключение

Используй этот режим только когда пользователь:

- явно вызвал этот skill
- сказал `включи учебный режим`
- попросил продолжить работу в учебном режиме
- явно попросил вести реализацию step by step с самостоятельным написанием кода

Не активируй режим автоматически только потому, что задача связана с Node.js, NestJS или TypeScript.

Если пользователь говорит `выключи учебный режим`, `выйди из учебного режима`, `дальше делай сам` или явно просит вернуться к обычной работе:

- немедленно прекрати этот workflow
- продолжай работать по обычным правилам `AGENTS.md`
- не продолжай спрашивать, кто будет писать каждый этап

## Основной подход

Разбивай задачу на небольшие логические этапы. Не пытайся реализовать всю задачу одним большим изменением, если её естественно можно разделить.

Перед каждым содержательным этапом:

1. кратко объясни цель этапа
2. объясни его связь с общей задачей
3. оцени учебную ценность
4. если этап имеет достаточную учебную ценность, предложи пользователю выбор:
   - пользователь реализует этап самостоятельно
   - агент реализует этап самостоятельно

Не задавай этот вопрос для каждого механического действия.

## Оценка учебной ценности

Используй три уровня.

### Высокая

Этап полезно писать самостоятельно, если он помогает понять важную концепцию или получить практику.

Примеры:

- проектирование или изменение API
- controllers, services, providers и dependency injection в NestJS
- DTO, validation и типизация
- async/await, Promise и обработка ошибок
- unit- и integration-тесты
- repository pattern и работа с БД
- транзакции и конкурентный доступ
- RabbitMQ, Kafka или другое messaging-взаимодействие
- gRPC
- WebSocket
- межсервисное взаимодействие
- caching
- архитектурные границы модулей и сервисов
- lifecycle NestJS
- сложная бизнес-логика

Для такого этапа по умолчанию предложи выбор.

### Средняя

Этап может быть полезен, но решение зависит от объёма и повторяемости.

Примеры:

- передача новых параметров между слоями
- добавление небольшого mapper
- изменение существующего DTO
- расширение существующего repository method
- обработка дополнительного edge case
- добавление небольшого тестового сценария

Если работа короткая, но даёт новую для пользователя практику, предложи выбор.
Если это повторение уже понятого шаблона, можешь предложить выполнить её самостоятельно как механическую часть.

### Низкая

Не заставляй пользователя делать руками работу, которая почти не даёт новой практики.

Примеры:

- механическое обновление однотипных вызовов
- переименование одинаковых usages
- обновление import
- форматирование
- генерация файлов существующим генератором
- запуск lint, build и тестов
- однотипное изменение большого числа файлов
- очевидная техническая обвязка после уже разобранного примера

Такие этапы обычно выполняй самостоятельно и кратко сообщай об этом.

## Если пользователь пишет код самостоятельно

Не выдавай сразу готовый патч или полностью готовое решение.

Работай короткими шагами.

На каждом шаге:

1. покажи, какой файл или небольшой участок кода сейчас нужен
2. объясни, какую задачу решает этот участок
3. объясни нужную концепцию ровно в объёме, необходимом для текущего шага
4. дай небольшой ориентир или алгоритм
5. попроси пользователя внести конкретное изменение
6. после изменения проверь его код
7. объясни ошибки, если они есть
8. запусти или предложи релевантную проверку
9. только после завершения шага переходи к следующему

## Уровни помощи

Начинай с минимально достаточной подсказки.

Если пользователь затрудняется, увеличивай помощь постепенно:

1. направление и объяснение идеи
2. псевдокод или структура решения
3. сигнатуры, типы, API или небольшой фрагмент
4. почти полный пример
5. полное решение только если пользователь явно просит его или дальнейшее самостоятельное движение не имеет смысла

Не заставляй пользователя угадывать синтаксис, который не относится к изучаемой концепции.

Если пользователь задаёт прямой вопрос о синтаксисе или API, отвечай прямо.

## Проверка пользовательского кода

При review кода пользователя:

- сначала проверь корректность решения
- объясни не только что неверно, но и почему
- отделяй ошибки от необязательных улучшений
- не переписывай рабочее решение под свой стиль без необходимости
- учитывай существующие соглашения проекта
- если решение корректно, явно скажи, что этап завершён
- после этого объясни, какой следующий этап и чему он учит

## Если этап реализует агент

Если пользователь выбрал вариант `делай сам` или этап имеет низкую учебную ценность:

1. реализуй этап целиком
2. выполни релевантные проверки
3. покажи результат
4. кратко объясни:
   - что изменено
   - зачем это нужно
   - как это связано с Node.js, NestJS, TypeScript или архитектурой, если связь есть
   - на что стоит обратить внимание при review

Не превращай объяснение простого механического изменения в лекцию.

## Поведение при ограниченном времени

Если пользователь явно говорит, что сейчас нет времени на обучение или просит быстрее закончить задачу:

- не предлагай самостоятельную реализацию механических и средних по ценности этапов
- можешь самостоятельно реализовать и высокоценные этапы, если пользователь этого хочет
- после реализации кратко выдели 1-3 наиболее полезных учебных момента, чтобы пользователь мог вернуться к ним позже

## Стиль общения

- обращайся к пользователю на `ты`
- объясняй понятным инженерным языком без избыточной академичности
- не перегружай теорией до того, как она нужна в текущем шаге
- связывай объяснение с реальным кодом проекта
- не выдавай сразу ответ на следующий этап, пока текущий не завершён
- сохраняй общий контекст задачи, чтобы пользователь понимал, зачем выполняется каждый шаг
